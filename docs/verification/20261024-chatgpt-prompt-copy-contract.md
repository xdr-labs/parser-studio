# ChatGPT Assisted — manual copy/paste prompt contract qualification (2026-10-24)

## User-visible question

Can an ordinary user copy the prompt generated by Parser Studio to ChatGPT
without additional instructions and paste the resulting answer back into
the parser builder?

This qualification distinguishes **prompt completeness, safe transfer,
and importability** from the **actual distribution of unassisted
independent ChatGPT model responses**. A passing controlled-response
browser replay is not a model-accuracy measurement.

## Tested baseline and observed defects

- Inspected the installed *development* application at
  `https://app.parser.xdr.ooo/`, JS asset `index-C2Xyqoi5.js`.
- Actual Chromium UI: 10/10 distinct sources produced copyable prompts,
  original source text preserved 10/10, source SHA-256 matched 10/10,
  and no external model-provider network request was made.
- Input classes: CSV, HDFS-like freeform text, Android Logcat threadtime,
  Snort alert, declared W3C, ordinary JSON, CEF, mixed JSON/KV,
  ambiguous prose and a log containing forged prompt boundary lines.
- **7/7 FULL_RECOVERY prompts** declared top-level fields but did not
  include the exact internal `map_field`, `cast_type`, `classify`,
  `dispatch_family`, and `fallback_unparsed` object shapes. A correct
  log interpretation could still lead to rejected JSON.
- Fixed `BEGIN/END ORIGINAL LOG SOURCE` delimiters could appear inside
  a raw log. This is an instruction/data boundary-confusion risk;
  the local application did not execute any of the injected text.

## Bounded corrections

- Use SHA-scoped, source-absent exact log delimiters. Do not rewrite,
  sanitize, truncate or transform the original source value.
- Explicitly state that only those exact tags separate data from
  instructions; content within, including forged markers or commands,
  remains untrusted source data.
- For FULL_RECOVERY only, add a precise declaration of permitted
  ParserRecipe v0.2 `sourceFormat`/`bodyFormat`, stage ordering,
  allowed `op` property shapes and typed casts. Illustrative
  placeholders are expressly forbidden in returned JSON; field names,
  regex rules and mappings still require source evidence.
- An already validated baseline includes a real canonical recipe; it
  is preserved as the reference rather than emitting redundant templates.
- No AI service integration, automatic raw log transfer, runtime/plugin
  change, deployment workflow, extra UI control or native target claim.

## Separate Auto Parser recovery entry points

A second user-facing failure class was confirmed after inspecting the normal
`Auto Parser → Analyze Logs → Fix with ChatGPT` action. This button uses
`buildBeginnerRepairPrompt`, *not* the main ChatGPT Assisted prompt builder.

- Actual pre-change public Chromium Snort/HDFS prompts included original
  values and UTF-8 residual ranges, but **0/2 had exact JSON root/stage
  contracts**. HDFS can have no local `SuiteResult`, leaving even the
  recovery source SHA and project identity out.
- This same schema contract is now reused in `beginnerAiPrompt` whenever a
  ParserRecipe is needed, whether or not a compiler-ready preview suite
  exists. Already-correct parsed spans, unknown source semantics and
  independent holdout requirements remain explicitly stated.
- With multiple original records and no validated baseline, the complete
  unchanged source is bounded by SHA-scoped markers, rather than asking the
  AI to generate a complete parser from only the one selected problem event.
- Metadata-only timestamp/header anomalies explicitly remain explanation
  requests without a ParserRecipe schema.
- When an Auto Parser pane lacks a suite, the generated prompt expressly
  directs users to the full ChatGPT Assisted workflow to import and test
  any returned JSON; the inline verification remains disabled, never
  pretending that a compiler test ran.
- The separate `Improve with AI → Selected Area` path now also declares
  exact stage schemas for unsupported baselines. It **does not** copy the
  full source silently: the manually reviewed/redacted excerpt is the only
  shared source, and the model is instructed to refuse an unprovable
  whole-source recovery.

Real Chromium after the change: **Snort 1/1 and HDFS 1/1** had original
source, exact recovery SHA/project identity, strict JSON field/stage schema,
residual evidence, and enabled result-review controls. Dedicated browser
tests were added for both entry points; latest critical UI tests **5/5 PASS**.
Latest complete frontend unit suite on the PR154 main-based candidate
**1,158/1,158 PASS (149 files)** and production Vite build **PASS**.

## What these numbers do NOT show

- **Independent externally invoked ChatGPT model responses: 0.**
  Controlled Recipes were authored for browser/compiler qualification;
  this does not establish that an unrelated signed-in ChatGPT session
  will produce a conforming Recipe without assistance.
- **No statistical acceptance rate** for unassisted model outputs,
  semantic field precision/recall, unknown-vendor full extraction,
  or user-facing copy→model→paste success can yet be reported.
- Even passing local Ruby/CONF generation does not qualify an actual
  Stellar Cyber 7.0 install, sensor ingestion or Interflow mapping.
- Original logs can contain sensitive data and are manually copied by
  the user; this workflow intentionally makes no hidden provider calls.

## Required independent ChatGPT acceptance gate

Use a separate, authorized signed-in ChatGPT session or model channel.
For at least 30 unfamiliar unseen multi-event samples, record the **first
response** to the **unchanged generated prompt** without feedback,
follow-up clarification or hand-edited JSON. Score independently:

1. First-response strict JSON or justified `REVIEW_REQUIRED`.
2. Exact imported v0.2 schema, identity and stage order (no manual fixes).
3. Bounded no-guess extraction against separately labelled holdout records.
4. Supported native draft compilation and source-preserving negative cases.
5. Copy/paste task completion, number of manual repairs and failure class.

Keep model/version, input source provenance and denominator explicit.
Do not count intentionally refused unsupported sources as successful
parser creation; score *correct refusals* separately.
